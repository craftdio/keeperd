# KeepERD — Storage & Backups

[Overview](../../README.md) · [Install](SETUP.md) · [Usage](README.md) · [Backup & Restore](#backup-and-restore)

KeepERD saves ERDs, layouts, colors, Areas, notes, filters, and recovery backups to a **local SQLite file**. There is no SQLite server, database account, or cloud storage to configure.

PostgreSQL 17 is used separately in temporary Docker containers to reproduce schema files during Sync. It does not store your workspace, and KeepERD does not require a production database connection.

## Where your data lives

On macOS, the default directory is `~/Library/Application Support/KeepERD/`.

| Location         | Contents                                                                                     |
| ---------------- | -------------------------------------------------------------------------------------------- |
| `keeperd.sqlite` | Edited ERDs, repository layouts, filters, settings, revisions, and bounded recovery backups. |
| `config.json`    | Personal configuration and registered local clones or worktrees.                             |
| `data/`          | Schema snapshots generated by Sync.                                                          |
| `repositories/`  | Internal GitHub repository clones.                                                           |

Homebrew and source builds use the same default data directory. Upgrading the app does not move it. `KEEPERD_STATE_DIR` can select another absolute path; use the same value for start and stop.

Browsers and profiles connected to a server using the same directory read the same saved workspace. This is shared persistence, without live merging of simultaneous edits. On a save conflict, export unsaved work as diagram JSON, then refresh. Sync snapshots are not backups of later editor changes.

## Backup and restore

### Share or move a layout

Use the editor's workspace-sharing action to export layout JSON. Import it into an ERD from the same repository; matching tables can receive layouts across different branches and commits. See [layout sharing](README.md#share-layouts).

For a full edited diagram, use the editor's diagram JSON export.

### Back up the whole workspace

1. Stop the server with `keeperd stop`.
2. Copy the entire KeepERD data directory to your backup location.
3. Start KeepERD again with `keeperd start`.

To restore, stop KeepERD, preserve the current directory separately, restore your backup directory, and start again. Copying only a live `keeperd.sqlite` can miss recent WAL commits. If preserving files after an abnormal shutdown, keep `keeperd.sqlite`, `keeperd.sqlite-wal`, and `keeperd.sqlite-shm` together when present.

## Automatic recovery backups

Backups are attempted before Sync replaces a schema or a full diagram/layout import replaces work. Ordinary dragging does not create a full backup each time.

- Up to **3 backups per ERD**, **128 overall**, and **32 MiB of UTF-8 backup payload**.
- Older backups are removed when limits are exceeded. Oversized individual backups are skipped with a warning.
- A regular backup failure warns and can allow the main change to continue. A main workspace write failure rolls back the save.

These backups are bounded recovery data on the same disk. Keep separate exported files or directory backups for long-term recovery. Payload limits do not describe the SQLite file's actual disk size.

## Migrate older browser data

Open the upgraded app once at the **original address and port in each original browser or profile**. KeepERD reads existing IndexedDB/localStorage data automatically and preserves the original browser data. It cannot read a browser or profile you have not opened.

For the same ERD, migration compares whole-diagram saved timestamps and adopts the latest complete edit. This is not a table-by-table merge; clock errors can affect ordering. Existing Git revision differences are reconciled with the current schema, and displaced copies are kept as recovery backups within the same limits.

If migration fails, existing server work remains available and migration is retried on a later visit. Export any unsaved work from older open tabs before closing them. For an older checkout's `.local-erd` folder, use the explicit source migration command in the [setup guide](SETUP.md).

<details>
<summary>Runtime and storage internals</summary>

The CLI and server require **Node.js 26.12.1**, which includes SQLite **3.54.0**, matching `.nvmrc`, `.node-version`, and `package.json`. Homebrew installs this runtime privately and launches KeepERD with it; you do not install Node yourself. The formula verifies the bundled runtime and SQLite persistence. Source developers must use the pinned version.

Storage uses Node's built-in `node:sqlite`, WAL, `synchronous=FULL`, and revision checks. Browser requests go through the local `/api/workspace` endpoint. Other ChartDB web builds retain their IndexedDB storage behavior. SQLite is not served as a static download.

`diagrams` stores complete edited ERDs; `layouts` stores repository-wide placements; `filters` and `meta` store settings and revisions; `backups` stores recovery copies; `imports` tracks browser migration hashes. Migration keeps original browser data, avoids duplicate imports, and rolls back its data and hash together on failure.

For manual migration-backup recovery, inspect `/api/workspace` for backups with `kind: "migration"`, then save the `value` from `/api/workspace?backup=<id>` as JSON for diagram import. Backup retention still applies.

Saved-ERD deletion updates SQLite and schema snapshot files separately. If deletion partly fails, refresh and retry the remaining entries. Deleting a saved ERD applies across browsers; it does not delete the user's source repository.
